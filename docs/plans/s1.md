# S1 — Server foundation

> Status: **in progress** · Created: 2026-10-30 · Owner: Felix

S1 builds the server everything after it stands on: persistence on two databases, local identity,
folders with permissions, managed automations, variables and secrets, an audit log and an API
reference. No runs, job queue, runner or web UI yet — those are S2 and S3.

## Fixed decisions

| Topic | Decision |
|---|---|
| Scope | Platform **plus managed automations** (create, edit, version, validate, move in folders), so permissions protect a real object from the start. Runs stay in S2. |
| Databases | PostgreSQL **and** SQLite from S1; EF Core for the model, provider-specific work behind narrow ports, one migration set per provider, every persistence test on both (ADR-0010, supersedes ADR-0005). |
| Identity | Own lean user store: password hashes, database-backed cookie sessions, personal API tokens; no ASP.NET Core Identity (ADR-0011). |
| Permissions | Instance roles Admin/User; folder roles Viewer/Operator/Editor/Owner granted to users and groups, inherited down the tree, cut by restricted folders (ADR-0012). |
| Secrets | AES-256-GCM per value with a key id, master key from environment or file; scope chain instance → folders → automation (ADR-0013). |
| API | Minimal APIs under `/api/v1`, RFC 9457 problem details, cursor pagination, `ETag`/`If-Match` for concurrency, OpenAPI generated at build and committed. |

## Design defaults

These are the starting point for the steps; a step that changes one records it here.

- **Ids and time**: ids are `Guid.CreateVersion7()`; the clock is an injected `TimeProvider`;
  timestamps are stored as UTC in a form that sorts correctly on SQLite.
- **Provider neutrality**: no SQL outside `AutoCanvas.Persistence.<Provider>`; JSON is stored as
  text, not `jsonb`; case-insensitive uniqueness uses a normalized column, not collations.
- **Errors**: every non-2xx response is a problem details document with a stable `type`; validation
  problems for automations carry the Core diagnostics (code, message, line, column).
- **Audit**: application services call an explicit `IAuditLog` inside the same transaction as the
  change. No interceptor magic; secret values never reach the audit log.
- **First admin**: `autocanvas-server admin create` and `AUTOCANVAS_BOOTSTRAP_ADMIN_*` for
  containers. The setup wizard is S4.

## Projects

```
src/AutoCanvas.Server/                 host: minimal APIs, authentication, DI, CLI subcommands
src/AutoCanvas.Server.Application/     use cases, PermissionEvaluator, IAuditLog, ports
src/AutoCanvas.Persistence/            EF Core DbContext, entities, configuration (provider-neutral)
src/AutoCanvas.Persistence.Postgres/   Npgsql provider, migrations, provider adapters
src/AutoCanvas.Persistence.Sqlite/     SQLite provider, migrations, provider adapters
tests/<Project>.Tests/                 one test project per source project, coverage per pair
```

Step 2 may merge projects if a boundary proves artificial; the decision is recorded here. Tests use
Testcontainers for PostgreSQL (overridable with `AUTOCANVAS_TEST_POSTGRES` for machines without
Docker), SQLite on a temporary file, and `WebApplicationFactory` for API tests.

## Steps

Each step is one PR into `main`; steps may split into smaller PRs as in S0.

### Step 1 — Plan and decisions

This plan; ADR-0010 (database providers), ADR-0011 (identity), ADR-0012 (permissions), ADR-0013
(secrets); `docs/technical/security.md`; architecture building blocks updated.

### Step 2 — Server skeleton

Host project with validated options, `/health/live` and `/health/ready`, problem details, OpenAPI
generated at build into `openapi/v1.json` with a CI check that it is not stale, structured logging,
`TimeProvider`, API test harness, nested `src/AutoCanvas.Server/AGENTS.md`.

### Step 3 — Persistence and audit infrastructure

DbContext and the two provider projects, first migration per provider, migrate on start
(configurable) and a `migrate` subcommand, the dual-provider test fixture, Testcontainers in CI,
`IAuditLog` with `audit_events`. Skill `add-migration` (both providers, always together). New
dependencies go through the license check and `dependencies.md`.

### Step 4 — Identity

Users, groups and membership; password hashing; login, logout, sessions with sliding and absolute
expiry; API tokens; login rate limiting; admin API for users and groups; bootstrap admin. Every
change is audited.

### Step 5 — Folders and permissions

Folder tree (materialized path; create, rename, move; deleting a non-empty folder is refused),
grants API, restricted flag, the pure `PermissionEvaluator`, endpoint filters
(`RequireFolderRole(...)`), list queries filtered by visible folders.

### Step 6 — Managed automations

Create, update, move and delete automations in folders; immutable versions with author and
message; validation through `AutomationLoader` with diagnostics in the problem details; names unique
per folder; `ETag` concurrency; YAML export.

### Step 7 — Variables and secrets

Instance, folder and automation scopes; AES-GCM encryption with key id; master key handling and
`admin rotate-master-key`; resolution chain and an *explain* endpoint that never returns secret
values; `SecretRedactor` harvested into Core for log redaction in S2. User doc *Variables and
secrets*.

### Step 8 — Audit queries, API reference, close

Audit query API (filters, cursor paging, retention), OpenAPI rendered on the docs site, user doc
*Users, folders and permissions*, operations doc (configuration, master key backup, migrations,
choosing a database), outcome and carry-over in this plan.

## Out of scope

Runs, job queue, scheduler, webhooks and runner (S2); web UI (S3); setup wizard and compose package
(S4); forges and repository automations (S5); OIDC, two-factor authentication and token scopes
(later).

## Carried over from S0

- Cache parsed expressions per automation version — used once runs exist (S2).
- Parser allocations (~100× file size) — revisit if loading becomes frequent.
- Node types as plugins — decide in S2.

## S1 done when

- All step PRs merged, `main` green.
- The server starts against PostgreSQL and against SQLite, migrates, and passes the same API tests
  on both.
- A scripted smoke run works on both databases: create the first admin, log in, create a token,
  create a folder, grant it to a group, create an automation as editor, read it as viewer, get
  `403` when the viewer edits, set a secret that never appears in any response or log, and find all
  of it in the audit log.
- Security model, operations and permissions are documented; the API reference is on the docs site.
