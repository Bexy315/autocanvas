# S2 — Runs

> Status: **in progress** · Created: 2026-10-31 · Owner: Felix

S2 makes automations run: triggers start runs, a job queue on both databases hands jobs to runners
over the gRPC runner protocol v1, the .NET reference runner executes them in containers, and the
server keeps their logs and test and coverage reports. No web UI yet — runs are read through the
API (S3).

## Fixed decisions

| Topic | Decision |
|---|---|
| Protocol | gRPC, spec first, one bidirectional control stream, chunked report upload ([ADR-0004](../adr/0004-runner-protocol-grpc-spec-first.md)); the server resolves one step at a time and decides results, secrets travel only with the step that uses them ([ADR-0008](../adr/0008-server-resolves-steps.md)). |
| Queue | AutoCanvas's own, with leases renewed by runners: PostgreSQL `SKIP LOCKED` + `LISTEN/NOTIFY`, SQLite one process with serialized claims ([ADR-0010](../adr/0010-database-providers.md)). |
| Runs | A run keeps a copy of its automation file and survives the automation; jobs per run, one row per attempt with the lease, steps per attempt; run numbers per automation ([ADR-0015](../adr/0015-runs-queue-and-logs.md)). |
| Logs | Chunks in the database, redacted again by the server, deduplicated by sequence; live through Server-Sent Events ([ADR-0015](../adr/0015-runs-queue-and-logs.md)). |
| Executor | Containers only in the reference runner; host executor later. No Docker socket inside jobs; images are built with rootless BuildKit. |
| Node types | Built-ins `docker_build` and `http_request`; unknown types are refused on save; plugins after 0.1 ([ADR-0016](../adr/0016-built-in-node-types-first.md)). |
| Artifacts | After S2, with an additive protocol RPC and their own storage decision. |
| Triggers | Manual, schedule, webhook and `automation_completed` in S2; push triggers and checkout of an automation's own repository come with the forges (S5). |

## Design defaults

These are the starting point; a step that changes one records it here.

- **Run retention**: 90 days, the newest 20 runs per automation always kept; logs and reports go
  with their run. Setting `Runs:RetentionDays`.
- **Schedules**: cron (five fields, time zone) and intervals as in the format; evaluated with
  Cronos by a ticker in the server; with PostgreSQL one server ticks (advisory lock). Times missed
  while the server was down are not replayed; the next one runs.
- **Webhooks**: `POST /api/v1/hooks/{token}`, the token shown once and stored hashed; optional
  HMAC-SHA256 signature over the body; body ≤ 1 MiB; rate limited per token; the body, selected
  headers and the query become `trigger.body`, `trigger.headers`, `trigger.query`.
- **Permissions**: starting and cancelling runs needs Operator on the automation's folder, reading
  runs and logs Viewer ([ADR-0012](../adr/0012-folder-permissions.md)); registering runners and
  creating registration tokens is for admins.
- **Runner authentication**: the gRPC endpoints accept only runner credentials, never user
  sessions or API tokens; credentials are stored hashed like API tokens.
- **Packages** (exact versions, published at least two weeks before they are taken):
  Grpc.AspNetCore and Grpc.Net.Client 2.84.0, Grpc.Tools 2.84.0, Google.Protobuf 3.36.2
  (Apache-2.0 / BSD-3-Clause), Cronos 0.13.0 (MIT), Docker.DotNet.Enhanced 4.3.3 (MIT; the
  original Docker.DotNet has had no release since 2023, and Testcontainers already uses the fork).

## Steps

Each step is one PR into `main` unless noted; steps may split as in S1.

### Step 1 — Plan and decisions

This plan; ADR-0015 (runs, queue and logs), ADR-0016 (built-in node types first).

### Step 2 — Run model and manual runs

Tables for runs, jobs, attempts and steps; copy of the automation file; run numbers; `RunService`
(start manually, cancel, list, get) and a `RunEngine` that applies `RunPlanner` actions and the
automation's `concurrency`; API and audit (`run.started`, `run.cancelled`). Jobs wait in the queue —
no runner yet.

- **2a — model, engine, use cases** *(done)*: tables `runs`, `run_jobs` (with their position in the
  file), `job_attempts` (migration `AddRuns`); steps per attempt come with step 4, when runners
  report them. A run belongs to its automation's folder (permissions) and keeps its id only while
  the automation exists; deleting the folder — possible once its automations are gone — removes the
  runs left in it. Run numbers are the highest so far plus one under a unique index; a start that
  loses a race counts again. `RunEngine` applies `StartJob` (queues attempt 1), `SkipJob`,
  `CompleteSwitch`, `CompleteJoin` and `CancelJob` and closes the run with `RunOutcome`.
  Expressions read `trigger.*` (from the run's trigger data), `run.*`, `vars.*` and `secrets.*`;
  `ConfigurationService.ResolveForRunAsync` resolves them for the run's own copy of the file, also
  after the automation was deleted. Starting by hand needs `triggers.manual: true`; with
  `concurrency: single` a second active run is refused (409). Cancelling cancels queued attempts;
  stopping running ones comes with the runner protocol.
- **2b — API and docs** *(done)*: `POST /automations/{id}/runs` (201 + Location),
  `GET /automations/{id}/runs`, `GET /runs/{id}`, `POST /runs/{id}/cancel`; user guide *Runs*;
  managed automations explain that runs outlive them.

### Step 3 — Job queue

The queue port with its PostgreSQL and SQLite implementations: claim by labels and node types,
leases, not-before times for retries (`RunPlanner.RetryDelay`), timeouts and a sweeper for expired
leases. Concurrency, lease-expiry and restart tests on both databases; dispatch latency benchmark
in `docs/technical/performance.md`.

### Step 4 — Runners on the server

Registration tokens and runner credentials; `RegistrationService` and `RunnerService.Connect`:
welcome, heartbeats, offers, reconnect with active jobs; resolving each step (environment,
expressions with `trigger`, `run`, `steps`, `jobs`, `vars` and `secrets` via
`ConfigurationService.ResolveAsync`, `mask_values`); step and job results through `StepPlanner`
and `RunPlanner`; cancellation; runner administration API. Tested with an in-test protocol client.
Likely 4a (registration, stream, leases) and 4b (steps, results, cancellation).

### Step 5 — Logs

Log chunk ingestion with deduplication and gap detection, redaction with `SecretRedactor`, storage
as chunks, masked outputs; API for a job's log by range and a live tail over Server-Sent Events.

### Step 6 — Reports

`UploadReport`, parsed with `AutoCanvas.Reports`, stored normalized (cases, counts, coverage,
warnings, truncation); API per run and job; test history by full name.

### Step 7 — Reference runner

`src/AutoCanvas.Runner`, adapted from the origin's runner: `register` command, configuration,
gRPC client with backoff and reconnect, container executor (job container, one exec per step,
labels, cleanup after crashes), service containers with presets, explicit checkouts, report upload,
cancellation, and a container image. The service presets' images, environments and readiness
commands are defined once on the server. Likely 7a (client, executor, scripts) and 7b (services,
checkout, `docker_build`, `http_request`).

### Step 8 — Triggers

Schedules, webhooks and `automation_completed` as in the defaults above; audit; user docs.

### Step 9 — Close S2

Run retention; an end-to-end test with the real runner and Docker in CI on both databases; user
docs *Runs*, *Runners*, *Triggers*; operations (runner setup, gRPC behind reverse proxies);
outcome and carry-over in this plan.

## Out of scope

Web UI (S3); setup wizard, compose package and runner registration UX (S4); forges, push triggers
and repository automations (S5); artifacts; host executor; node plugins; OIDC, two-factor
authentication and token scopes (later).

## S2 done when

- A runner registers with a one-time token and connects over gRPC, on both databases.
- A manual run of an automation with a service container and two dependent jobs succeeds on the
  real runner; its log arrives live and a secret appears only as `***`; its TRX and Cobertura
  reports are readable through the API.
- A schedule and a signed webhook start runs; cancelling, retrying and an expired lease (runner
  killed mid-job) behave as specified.
- Everything that changes something is in the audit log; the docs and the API reference cover runs,
  runners and triggers.
