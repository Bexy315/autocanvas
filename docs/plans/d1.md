# D1 — A throwaway dev instance

> Status: **in progress** · Created: 2026-11-05 · Owner: Felix

S0–S5 built what the roadmap in [S0](s0.md) asked for before 0.1. Before 0.1, the maintainer wants
an instance to test by hand that:
- always runs the newest `main`;
- starts from a known state again by itself;
- looks like a real installation from the [compose package](../../deploy/compose/).

D1 builds it:
- CI publishes the images;
- a seed script fills a fresh instance with test users and automations;
- a GitHub Actions workflow deploys `main` to a VPS and resets it.

Everything is generic: the domain, the VPS's address and the credentials are settings of the
repository on GitHub, not part of the repository, so others can run the same for their own forks.
[ADR-0023](../adr/0023-published-images-and-dev-instance.md) records the decisions.

The publishing of images is also what 0.1 needs, so D1 also covers part of the carried-over
*Publish the images with the first release* ([S5](s5.md#carried-over-to-s6)).

## Fixed decisions

Felix decided these on 2026-11-05.

| Topic | Decision |
|---|---|
| Resets | A deploy after a merge **keeps the data**, so it also tests the migrations on a filled database. The instance is **reset every night** and **on demand** (a button in GitHub Actions). |
| Deploying | **GitHub Actions over SSH**, with a key that may only run the deploy script on the VPS. |
| Access | **Cloudflare Access** in front of the whole instance (the maintainer sets it up), except the webhook paths, so forges can still call them. The test users' passwords may then be simple. |
| Where | **In this repository, generic**: `deploy/dev/` and a workflow; the domain, the VPS and the credentials are GitHub secrets and variables. |
| Images | **GitHub Container Registry**: `ghcr.io/<owner>/autocanvas-server` and `-runner`, tagged with the commit and `dev`. |
| Seed | An admin; users with Viewer, Operator and Editor rights; a group; folders with automations that produce tests and coverage; a secret. **No GitHub App** yet (the maintainer still tests that by hand; it may come later). |
| Host | A VPS with 4 cores and 8 GB, **Ubuntu 24.04**, the compose package with **PostgreSQL**. |

## Design defaults

- **Images**:
  - built on every push to `main` (and by hand) by a workflow of their own, for `linux/amd64`;
  - tagged `sha-<commit>` and `dev`;
  - with the commit in the server's version (`GET /api/v1/info`, already shown in the web UI), so a
    tester sees which commit runs.

  Releases later add version tags to the same workflow. As long as the repository is private, so
  are the images.
- **Pulling without a stored token**: the deploy passes the workflow's short-lived `GITHUB_TOKEN`
  (`packages: read`) to the VPS on standard input. The deploy script logs in, pulls and logs out,
  so no lasting registry credential lives on the VPS.
- **The deploy key** is restricted in `authorized_keys`:
  - `restrict` and a forced `command=`, so it runs only `deploy/dev/remote.sh`;
  - that script takes `deploy <commit>`, `reset` or `status` from `SSH_ORIGINAL_COMMAND` and
    nothing else.

  The deploy user is in the `docker` group, which is root on that host in effect; the forced
  command is what keeps the key from being a shell. The admin key for setting up the host is a
  different one and stays with the maintainer.
- **The instance**:
  - `deploy/compose` with `compose.postgres.yaml`, plus `deploy/dev/compose.dev.yaml`;
  - the dev file adds a **Caddy** in front, with Cloudflare's origin certificate, and binds the
    server's ports to the Docker network only;
  - the bundled runner reaches the server inside it, and the runner port stays closed outside.
  - The public address and trusted proxies are set by the seed and the dev file.
- **Firewall** (`ufw`): 443 only from Cloudflare's address ranges; 22 for keys only (no
  passwords, no root login); nothing else.
- **Seed** (`deploy/dev/seed.sh`, bash with `curl` and `jq`, through the public API only):
  1. the setup with the token from the server's log;
  2. users, a group, grants, folders, automations and a secret;
  3. a first run of each automation, so runs, tests and coverage are there to look at.

  The passwords come from one secret. The seed only runs on a fresh instance and refuses
  otherwise. CI runs it against the compose package, so it breaks in the PR that breaks it, not at
  night.
- **Deploy** (`remote.sh deploy <commit>`):
  1. pull both images at that commit;
  2. `docker compose up -d`, which runs the migrations;
  3. wait for `/health/ready` and check that `/api/v1/info` names the commit;
  4. remove older AutoCanvas images on the VPS, keeping the last three so a deploy can be undone by
     hand.

  A failed check fails the workflow.
- **Reset** (`remote.sh reset`): `docker compose down --volumes` (data, master key, runner
  workspaces), start the current images, seed. The master key is new after every reset; nothing on
  the dev instance is meant to outlive a night.
- **Workflow** (`.github/workflows/dev.yml`):
  - after the images workflow succeeds on `main`, it deploys;
  - a schedule resets every night (02:00 UTC);
  - `workflow_dispatch` offers *deploy* or *reset*;
  - one `concurrency` group, so deploys and resets never overlap.

  It uses the GitHub environment `dev` for the secrets. Environment secrets need a paid plan on
  private repositories, so until the repository is public they are repository secrets with the
  same names.
- **Seen from outside**: after a deploy or reset, the workflow's summary links the instance and
  names the commit.

## Steps

Each step is one PR into `main`.

### Step 1 — Plan and decision

This plan and ADR-0023.

### Step 2 — Published images

**Done**:
- **`images.yml`** publishes both images to GHCR on every push to `main` and by hand:
  - `sha-<commit>` and `dev`, `linux/amd64`;
  - GitHub Actions' build cache per image;
  - login with the workflow's token (no third-party login action);
  - the pushed server image checked to name its commit.
- **The commit in the version**: the Dockerfiles take `SOURCE_REVISION` (as `SourceRevisionId`)
  and carry OCI labels (source, revision, license), so GHCR links the packages to the repository.
- **Checks**: `deploy/test/image-version.sh` starts a server image and compares its version with
  the commit. CI's *Server image* job runs it on every PR.
- **The install scripts** pass the checkout's commit too.
- **Docs**: *Using the published images* in the installation guide; the container image and updates
  in operations.

**Planned**:

- **`images.yml`**: on pushes to `main` and by hand, it builds both images and pushes them to GHCR
  with `sha-<commit>` and `dev`. It uses the build cache of GitHub Actions and `packages: write`
  for this workflow only.
- **The commit in the version**: the Dockerfiles take `SOURCE_REVISION` and pass it to the build,
  so `GET /api/v1/info` (and the web UI's footer) name it. A test checks the format of the version.
- **The compose package** reads the image names from `.env` already; the docs say how to use the
  published ones instead of building locally.
- **Review**: the images appear in the repository's packages after the merge.

### Step 3 — Seed

**Done**:
- **`deploy/dev/seed.sh`**: what the plan lists, through the public API only; the table is in
  `deploy/dev/README.md`.
- **Changes found while building**:
  - Users an admin creates must change their password at the first sign-in. The seed therefore
    creates them with an initial password and changes it as each of them, so they sign in with the
    seed password right away.
  - Validating a file needs the folder it goes into (`folderId`).
  - `Team / Restricted` holds an automation too, `deploy`, so that what only `editor` sees has
    content.
- **CI**: the *Compose package (postgres)* job runs `compose-smoke.sh --seed`. The seed itself fails
  unless the four first runs end as planned (three succeed, `fails-on-purpose` fails) and
  build-and-test's reports are as seeded. The check then signs in as each user, compares which of
  Team's folders they see, and seeds a second time, which must change nothing. The *sqlite* job keeps
  the plain smoke test.

**Planned**:

- **`deploy/dev/seed.sh`**: the seed above. It is idempotent in one sense: on an instance that is
  already set up, it stops and says so without changing anything.
- **CI**: the *Compose package (postgres)* job runs it after the install and checks the result
  through the API: the users can sign in, the automations exist, the first runs succeeded.
- **Docs**: what the seed creates, in `deploy/dev/README.md`.

### Step 4 — The host

- **`deploy/dev/bootstrap.sh`**, run once as root on a fresh Ubuntu 24.04:
  - Docker CE from Docker's repository;
  - unattended security upgrades;
  - `ufw` as above;
  - SSH without passwords;
  - the user `deploy` with the restricted key;
  - the instance directory with the dev compose files and the origin certificate;
  - Docker's log rotation.

  It can run again without harm.
- **`remote.sh`**, `compose.dev.yaml`, `Caddyfile`.
- **Doing it**: Claude runs the bootstrap on the maintainer's VPS with the maintainer's admin key,
  then the first deploy and reset by hand, through the deploy key.
- **The maintainer**, in Cloudflare:
  - the DNS record (proxied);
  - SSL mode *Full (strict)* and an origin certificate for the VPS;
  - Access for the instance, with a bypass for `/api/v1/hooks/*` and `/api/v1/forges/github/*`.
- **Review**: the instance answers through Cloudflare Access, the seed users can sign in, and the
  host is closed except 22 and 443.

### Step 5 — Deploying from GitHub Actions

- **`dev.yml`** as above, with the secrets `DEV_SSH_HOST`, `DEV_SSH_KEY`, `DEV_SSH_KNOWN_HOSTS`,
  `DEV_SEED_PASSWORD` and the variable `DEV_URL`.
- **Docs**: *A dev instance of your own* in operations: what it does, what to set, how to reset by
  hand.
- **Review**: a merge shows up on the instance with its commit; a manual reset brings back the seed
  state; the next morning shows the nightly reset in Actions.

### Step 6 — Close

The outcome and what is carried over, here; ADR-0023 accepted.

## Open questions

- **Notifications**: should a failed deploy or reset tell the maintainer beyond GitHub's own mail

## D1 done when

- A merge into `main` runs on the dev instance within minutes, with its commit shown in the UI.
- The instance resets itself every night, and on demand, to the seed state.
- Nobody reaches it without passing Cloudflare Access, except forges on the webhook paths.
- The seed and the images are checked in CI.
- The docs show how to run the same for a fork.
