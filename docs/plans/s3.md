# S3 — Web UI and canvas

> Status: **in progress** · Created: 2026-11-01 · Owner: Felix

S3 gives AutoCanvas a web UI. It covers signing in, folders and automations, a visual canvas next to
a YAML editor, runs with live logs, tests and coverage, triggers, variables and secrets, sharing,
and simple administration. Until now everything goes through the HTTP API. The canvas is harvested
from the origin's editor. The web gates specified in S0 are switched on with `src/web`.

The maintainer reviews the UI by eye: every step that changes what is visible ends with a
**Review** point. It says what to look at and how to start it locally.

## Fixed decisions

| Topic | Decision |
|---|---|
| Stack | As in the origin: React 19, Vite, TypeScript strict, `@xyflow/react` and `@dagrejs/dagre` for the canvas, Tailwind 4, Radix primitives, Lucide icons. TanStack Query holds API data and React Router handles navigation ([ADR-0018](../adr/0018-web-ui.md)). |
| Delivery | The server serves the built SPA from `wwwroot` on the same origin as the API, with a fallback to `index.html`, cache headers and a CSP. The UI uses the existing cookie session and CSRF header and needs no CORS. Server and UI ship as one process in one image ([ADR-0018](../adr/0018-web-ui.md)). |
| Editor | YAML stays the source of truth. The canvas edits the document in the browser with the `yaml` package's Document API, which keeps comments, and stores positions under `x-editor.layout`. A CodeMirror 6 YAML editor sits next to it, and both stay in sync. Diagnostics come live from the server, which checks with Core ([ADR-0018](../adr/0018-web-ui.md)). |
| Scope | Working and sharing: account, folders, automations, canvas and YAML, runs with live logs, tests, coverage, test history, triggers and webhooks, variables and secrets, sharing. Admin views for users, groups and runners stay simple. Runner registration with comfort and the setup wizard belong to S4. |

## Design defaults

These are the starting point; a step that changes one records it here.

- **Packages**:
  - exact versions, published at least two weeks before they are taken, as in `docs-site`;
  - `package-lock.json` committed;
  - npm licenses checked in CI against the same MIT-compatible list as NuGet;
  - one line per package in `docs/technical/dependencies.md`.
- **Location**: `src/web` (npm package `@autocanvas/web`). The build writes to
  `src/AutoCanvas.Server/wwwroot`, which is not committed. The server image builds the UI in a
  stage of its own.
- **Development**: `npm run dev` starts Vite with a proxy from `/api` to the local server.
  `build/dev.sh` starts the server (SQLite), a reference runner and Vite together.
- **Design**:
  - a plain look of its own, with Tailwind tokens (colors, spacing, type) in one file;
  - light and dark following the system setting, switchable;
  - usable by keyboard, with visible focus and WCAG AA contrast;
  - English texts like the docs and the API, with dates and numbers in the browser's format.
- **API access**:
  - types generated from `openapi/v1.json` with `openapi-typescript`, behind a thin `fetch` wrapper;
  - the wrapper always sends the CSRF header;
  - problem details are shown the same way everywhere: validation errors at their field,
    diagnostics in the editor;
  - changes send `If-Match` with the ETag they were based on.
- **Permissions**: the UI offers actions according to the role the API returns for folders and
  automations. The server stays the only check.
- **Tests**:
  - Vitest and Testing Library for logic and components, at least 75 % line coverage for `src/web`;
  - Playwright against the real server (SQLite) for the smoke test and walk-throughs; the reference
    runner and Docker are only needed by the end-to-end walk-through;
  - Playwright screenshots are kept as a CI artifact, so a change can be seen without starting it.
- **Missing API** is added by the step that needs it, additively and with the OpenAPI snapshot.
  Known so far:
  - validating a file without saving it;
  - a catalog of node types;
  - recent runs across automations;
  - finding users and groups when sharing, limited for non-admins.

## Steps

Each step is one PR into `main` unless noted; steps may split as in S2.

### Step 1 — Plan and decisions

This plan; ADR-0018 (web UI: stack, delivery by the server, YAML as the editor's source of truth);
`src/web/AGENTS.md` as the rules step 2 starts from.

### Step 2 — Scaffold and gates

- The Vite app with the gates in CI: typecheck, oxlint, Prettier, Vitest coverage, npm licenses and a
  Playwright smoke test.
- Delivery by the server: `UseStaticFiles`, the SPA fallback (never for `/api`, webhooks included,
  or `/health`), CSP and caching; the server's Dockerfile with a web stage.
- The app shell: navigation, light and dark, error display.
- Signing in and out, the forced password change, an expired session.

**Review**: signing in, the shell, both color schemes.

### Step 3 — Folders and automations

- The folder tree with breadcrumbs, and the automations of a folder.
- An automation's overview: title, description, triggers, latest runs.
- Versions with a diff, and the YAML download.
- Creating, renaming, moving and deleting, offered by role.

**Review**: navigation and lists.

### Step 4 — YAML editor

- CodeMirror with YAML. Diagnostics come from a new `POST /api/v1/automations/validate`, which runs
  Core's checks, the node catalog and the trigger checks without saving.
- Completion for keys and node types from a new `GET /api/v1/node-types`.
- Saving with a message, and a conflict when someone saved in between.

**Review**: editing and how errors are shown.

### Step 5 — Canvas

Harvested from the origin's `devops-web` (`src/features/editor`, `lib/flowConvert.ts`,
`autoLayout.ts`; skill `harvest`).

- **5a — model and view**:
  - YAML to graph and back for jobs, `needs`, switches with cases, joins and `finally`;
  - the dagre layout and positions in `x-editor.layout`;
  - a read-only canvas that follows the YAML editor.

  **Review**: the canvas next to YAML for the examples in `schema/examples/`.
- **5b — editing**:
  - a palette with job, switch, join and the node types;
  - drawing and deleting connections, selecting several nodes;
  - panels for jobs (`runs_on`, `image`, `env`, steps, services, checkout, reports, retry,
    timeout) and for triggers;
  - undo and redo; every change lands in the YAML document.

  **Review**: building an automation on the canvas. This is the most important review of S3.

Parts of a valid file that the canvas cannot edit are shown read-only, with a hint to use YAML.

### Step 6 — Runs

- The runs of an automation, and recent runs across automations (new endpoint).
- A run as a graph with each job's status.
- A job with its attempts and steps.
- The live log over Server-Sent Events: following and jumping, search, lines per step, ANSI colors.
- Starting by hand and cancelling.

**Review**: watching a real run on the local runner.

### Step 7 — Tests and coverage

- A run's reports with their totals.
- Tests filtered by outcome; failures with stack trace and output.
- Coverage by package and class, with the lines not covered.
- A test's history over time, with a hint when it is flaky.

**Review**.

### Step 8 — Triggers and configuration

- Schedules with their next times; `automation_completed`.
- Creating and rotating a webhook: the token and secret shown once, with copy buttons and a `curl`
  example.
- Variables and secrets for the instance, folders and automations, with the view that explains where
  a value comes from.

**Review**.

### Step 9 — Sharing and administration

- Folder roles for users and groups, and restricted folders.
- Users and groups for admins, simply.
- Runners: online status, pausing, renaming, deleting, and creating a registration token (simply).
- One's own API tokens and sessions.

**Review**.

### Step 10 — Close S3

- A Playwright walk-through of the whole way in CI, on the real server with the reference runner and
  Docker: sign in, build an automation on the canvas, save, start, follow its log, look at tests and
  coverage, share it.
- Docs: the user guide with screenshots, and an architecture page for the UI.
- Outcome and carry-over in this plan.

## Out of scope

- Setup wizard, compose package and runner registration with comfort (S4).
- Forges and repository automations (S5).
- Mobile layouts beyond "readable".
- Translations.
- An audit log view (admins, later).
- Editing together in real time.

## Carried over from S2

- Parser allocations (~100× file size) — revisit if loading becomes frequent; the validate endpoint
  of step 4 is a new caller.
- Dependabot for the docs site's npm packages, with the two-week minimum age; review the
  `npm audit` advisories in Docusaurus's toolchain then. `src/web` joins it in step 2.
- Forwarded headers behind a proxy (sign-in rate limit per client, full webhook URLs) — S4.
- Publish the runner image with the first release (0.1).
- `trigger.body` reads JSON objects by property name only; array indexes when someone needs them.
- Drop the two `.gitleaksignore` fingerprints when the branch history no longer matters.

## S3 done when

- A new user signs in and builds an automation on the canvas with two jobs, a service and a node
  step. They save it, start it and follow its log live.
- They see failed tests with their stack traces and the coverage, create a signed webhook, and share
  the folder with a group.
- All of this runs in CI as a Playwright walk-through on the real server with a runner.
- The web gates are green.
- The docs show the UI.
