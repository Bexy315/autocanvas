# S4 — Setup and packaging

> Status: **done** (2026-11-04) · Created: 2026-11-03 · Owner: Felix

S4 makes a running instance quick to get. One command creates the instance from a `docker compose`
package, with the server and a runner. A wizard in the browser then asks for the first admin, the
public address, registers the bundled runner and offers an example automation. Until now an
installation needs a master key, an admin command, configuration and a registered runner, each by
hand.

As in S3, every step that changes what is visible ends with a **Review** point for the maintainer.

## Fixed decisions

Felix decided these on 2026-11-03; [ADR-0020](../adr/0020-first-start-setup.md) records the
architecture.

| Topic | Decision |
|---|---|
| Way to an instance | A `docker compose` package in `deploy/compose/` and an install script (`deploy/install.sh`, `deploy/install.ps1`). The script creates an instance directory with `compose.yaml` and `.env`, builds or pulls the images, starts them and prints the setup address. The same package works by hand, following the docs. |
| Setup mode | A server without accounts and without `Bootstrap:*` starts in setup mode. It logs a setup address with a one-time token, and only the setup API and the UI answer until setup is finished. `admin create` and the bootstrap variables stay and skip the wizard. |
| Master key | When none is configured and the database has stored no key id, the server generates one into `Secrets:MasterKeyFile` (by default `keys/master.key` in its data directory; a volume of its own in the compose package). The wizard shows it once to be backed up. When the operator sets the key, nothing changes. |
| Wizard | It asks for: the first admin; the public address and the runner address (filled in from the browser); the bundled runner, registered automatically and waited for; an example automation (optional). It ends with the master key and the sign-in. |
| Instance settings | The public address and the runner address are kept in the database and changed in the wizard and under **Administration → Instance**. A value set in configuration wins and is shown as locked. |
| Images | Built locally from the checkout until 0.1; publishing them comes with the release. The compose file names the images as they will be published. |

## Design defaults

- **Package**:
  - SQLite by default; a `postgres` profile adds a PostgreSQL container with a password generated
    by the install script;
  - volumes for the data, the key and the runner;
  - the runner gets the Docker socket, as documented for the reference runner;
  - ports 5080 (UI and API) and 5081 (runners) by default, changeable in `.env`.
- **Install script**:
  - `install.sh` (POSIX sh) and `install.ps1` do the same;
  - no questions on the command line beyond the target directory and `--postgres`; everything else
    is asked in the browser;
  - running it again on an existing directory updates and restarts, and never overwrites `.env`.
- **Security**:
  - the setup token is compared in constant time and setup attempts are rate-limited;
  - finishing setup is one transaction;
  - the setup API is gone afterwards (`404`).
- **Tests**:
  - the server's setup mode on SQLite and PostgreSQL;
  - the wizard with Vitest and in Playwright;
  - the whole package in a CI job of its own: install, setup through the API, a run on the bundled
    runner.

### Step 1 — Plan and decisions

### Step 2 — Setup mode on the server

- **Setup mode**:
  - the setup token and its log line;
  - `GET /api/v1/setup` (whether setup is open);
  - `POST /api/v1/setup` (admin, settings, runner token, example; with the token);
  - every other API request answered with `503` while setup is open.
- **Generated master key**, recorded like a configured one.
- **Instance settings**: table, migrations for both providers, `GET`/`PATCH
  /api/v1/admin/instance`, configuration winning over the database.
- **Handing the runner token over** to a file on a shared volume (`Setup:RunnerTokenFile`).
- **Tests** on both databases, the OpenAPI snapshot, operations and user docs.

- **Done**:
  - **Setup mode** (`Setup/`):
    - the token lives in memory and is logged with the setup address once the server listens;
    - a gate answers every other API request with `503` (*setup required*) and closes setup mode as
      soon as an account exists;
    - `GET`/`POST /api/v1/setup` with the `X-AutoCanvas-Setup-Token` header, rate-limited (20 a
      minute per address).
  - **Completing the setup** (`SetupService`) creates the admin (no forced password change), the
    addresses, the example automation (`ExampleAutomation`, folder *Getting started*) and the runner
    token in one transaction, then signs the admin in; the response carries a generated master key.
  - **Generated master key**: `keys/master.key` in the data directory (mode 600), only when the
    server itself starts and no key is configured; the commands use the file but never create it.
    With a database that already has a key id, the new file is removed again and the server stops.
  - **Instance settings** (`instance_settings`, both providers):
    - `GET`/`PUT /api/v1/instance` for admins;
    - `Server:PublicUrl` and the new `Runners:PublicUrl` win and are locked;
    - the effective public address decides the `Secure` cookie.
  - **Settings**: `Setup:Enabled` (tests turn it off) and `Setup:RunnerTokenFile` (the token is
    written next to it and moved into place).
  - **Deviations**:
    - the API names the addresses `publicAddress` and `runnerAddress` (the analyzers want `Uri` for
      anything called *Url*);
    - `PUT` instead of `PATCH`, since the UI sends both values;
    - the endpoint is `/api/v1/instance` like the other admin resources, not under `/admin`.

### Step 3 — The wizard in the web UI

- **`/setup`**, outside the app shell:
  1. the token (filled in from the address);
  2. the first admin;
  3. the addresses, filled in from the browser;
  4. the bundled runner, waiting until it is online, or the commands for another runner;
  5. the example automation;
  6. a summary with the master key, shown once.
- After setup the browser signs in as the new admin.
- **Administration → Instance**: the addresses, locked where configuration sets them.
- Vitest, a Playwright spec with screenshots.

**Review**.

- **Done**: Felix chose steps with progress over one long form, and a token typed in when the
  address has none: on a server without a browser, the address in the log (`localhost`) cannot be
  opened, so `/setup` is opened on the server's address from another machine.
  - **`/setup`** (`pages/setup/`): Token → Admin → Addresses → Options in a wider sign-in card, then
    the master key (until confirmed), waiting for the bundled runner (skippable) and links into the
    app or to the example. A problem at a field sends the form back to its step.
  - **Recognized everywhere**: `isSetupRequired` (503, `setup-required`) sends the session guard and
    the sign-in page to `/setup` instead of retrying as if the server were down; a wrong setup
    token's 401 does not end a session.
  - **Administration → Instance** with locked addresses; the runner token dialog takes the runner
    address from there.
  - **e2e** `12-setup`: a server of its own in setup mode (`e2e/setupServer.ts` reads the token from
    its log), the setup with the token typed in, the master key compared with the file, the runner
    token file, the example and the Instance tab.

### Step 4 — Runner and compose package

- **4a done** (runner and server):
  - **The runner registers itself** with `Runner:RegistrationTokenFile` and `Runner:Name`: it waits
    for the file, retries while the server cannot be reached, stops on a refused token. The
    `register` command and the runner share `Connection/RunnerRegistration`.
  - **Forwarded headers** from `Server:TrustedProxies` (addresses or networks,
    `AUTOCANVAS_TRUSTED_PROXIES`): client address and scheme for rate limits, the audit log and the
    `Secure` cookie; ignored from anywhere else.
  - **Webhook addresses** come whole (`url`) when a public address is known.
  - **Images**: the key directory (mode 700) and the handoff directory exist and belong to `app`, so
    named volumes mounted there are writable.
- **4b done** (package):
  - **`deploy/compose/`**: `compose.yaml` (server with volumes `data`, `keys`, `handoff`; the bundled
    runner with the Docker socket and its group), `compose.postgres.yaml` through `COMPOSE_FILE`,
    `.env.example`.
  - **The runner's workspaces** live in a named volume; job containers mount them from the volume's
    path on the Docker host, read with `docker volume inspect` after `docker compose create`. This
    needs no host directories and no `chown`, and works with Docker Desktop as with Docker Engine.
  - **`deploy/install.sh` and `deploy/install.ps1`**: build the images from the checkout, write
    `.env` once (project name from the directory, socket group, a PostgreSQL password), start, and
    print the token from the server's log.
  - **CI "Compose package"** (SQLite and PostgreSQL): `deploy/test/compose-smoke.sh` installs, sets
    up through the API, waits for the runner `bundled` and runs the example with its tests and
    coverage.
  - **Docs**: *Installation* in the user guide, the package in operations, a quick start in the
    README.
- **Felix, 2026-11-03**: the install script prints the setup token and says to open `/setup` on
  this machine's address; it does not work out the machine's addresses itself.

- **Runner**: `Runner:RegistrationTokenFile` (wait for the file, register, run) and `Runner:Name`.
- **Package**: `deploy/compose/compose.yaml` with the server, the runner, volumes and the `postgres`
  profile.
- **Install scripts**: `deploy/install.sh` and `deploy/install.ps1`.
- **Forwarded headers** behind a proxy (`Server:TrustedProxies`): sign-in rate limits per client
  and full webhook addresses (carried over since S1).
- **CI job "Compose"**: the install script, setup through the API, a run of the example automation
  on the bundled runner, with and without PostgreSQL.

**Review**: Felix installs it on his machine.

### Step 5 — Close S4

- **Getting started**: a page on installing, the wizard and the first run, with pictures from a
  Playwright walk-through of the wizard against the compose package in CI.
- **Operations**: backing up the data and the key, updating, PostgreSQL, a proxy in front.
- Outcome and carry-over in this plan.

- **Done**: e2e `12-setup` now runs with a runner as the compose package does
  (`startBundledRunner`: an unregistered runner process waiting for the setup's token file), so the
  wizard sees `bundled` come online and the example runs with its tests and coverage. Without Docker
  the test goes on without the runner, except in CI. Its `install-*` pictures (light and dark) are
  in the *Installation* page; operations gained backups, updates and a proxy in front for the
  package. Deviation: the pictures come from this test, not from a browser against the compose
  package, which the CI job checks already; the job needs no browser that way. The token step reads
  the field from the form when it is sent, as a quick click after typing sometimes sent the value of
  the render before.

## Open questions

- **Bundled runner labels**: `linux` and `docker`, or chosen in the wizard? The runner announces
  its labels from its configuration, so choosing them would mean writing them to `.env` — proposed:
  fixed, changeable in `.env`.
- **Example automation**: proposed is one job on `alpine` that prints a greeting and writes a small
  JUnit and Cobertura report, so the first run shows the log, tests and coverage.

## Out of scope

- Published images, releases and a changelog (0.1).
- TLS inside the package; the docs show a proxy (Caddy, nginx) in front.
- Kubernetes and Helm.
- E-mail.
- OIDC.
- Several server instances in the package.

## Outcome

S4 delivered, in PRs #62–#67:

- **Setup mode** (ADR-0020): a fresh server logs a setup address with a one-time token and answers
  only its setup until the first admin exists; the setup creates the admin, the addresses, the
  example automation and the bundled runner's token in one transaction.
- **Generated master key** for fresh installations, kept apart in the package, shown once.
- **Instance settings**: the public and runner addresses in the database, locked where the
  configuration sets them; **Administration → Instance**.
- **Wizard** in the web UI: token (from the address or typed in, for servers without a browser),
  admin, addresses, options, master key, waiting for the runner.
- **Runner** registers itself from a token file.
- **Trusted proxies**: forwarded client address and scheme (carried over since S1); whole webhook
  addresses.
- **`docker compose` package** with install scripts for Linux, macOS and Windows; SQLite or
  PostgreSQL.
- **Quality**: 1,352 .NET tests; 332 Vitest tests; 13 Playwright tests, the setup among them
  with a self-registering runner; a CI job that installs the package and runs the example, with
  SQLite and PostgreSQL.
- **Docs**: *Installation* with pictures, setup and instance settings in operations, security and the
  API conventions.

Deviations, each recorded in its step: step 4 became two PRs (4a, 4b); Felix decided against working
out the machine's addresses anywhere (the token is typed in on `/setup` instead); the pictures come
from the e2e test rather than from a browser against the package.
