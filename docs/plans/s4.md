# S4 — Setup and packaging

> Status: **in progress** · Created: 2026-11-03 · Owner: Felix

S4 makes a running instance quick to get. One command creates the instance from a `docker compose`
package, with the server and a runner. A wizard in the browser then asks for the first admin, the
public address, registers the bundled runner and offers an example automation. Until now an
installation needs a master key, an admin command, configuration and a registered runner, each by
hand.

As in S3, every step that changes what is visible ends with a **Review** point for the maintainer.

## Fixed decisions

Felix decided these on 2026-11-03; [ADR-0020](../adr/0020-first-start-setup.md) records the
architecture.

| Topic | Decision |
|---|---|
| Way to an instance | A `docker compose` package in `deploy/compose/` and an install script (`deploy/install.sh`, `deploy/install.ps1`). The script creates an instance directory with `compose.yaml` and `.env`, builds or pulls the images, starts them and prints the setup address. The same package works by hand, following the docs. |
| Setup mode | A server without accounts and without `Bootstrap:*` starts in setup mode. It logs a setup address with a one-time token, and only the setup API and the UI answer until setup is finished. `admin create` and the bootstrap variables stay and skip the wizard. |
| Master key | When none is configured and the database has stored no key id, the server generates one into `Secrets:MasterKeyFile` (by default `keys/master.key` in its data directory; a volume of its own in the compose package). The wizard shows it once to be backed up. When the operator sets the key, nothing changes. |
| Wizard | It asks for: the first admin; the public address and the runner address (filled in from the browser); the bundled runner, registered automatically and waited for; an example automation (optional). It ends with the master key and the sign-in. |
| Instance settings | The public address and the runner address are kept in the database and changed in the wizard and under **Administration → Instance**. A value set in configuration wins and is shown as locked. |
| Images | Built locally from the checkout until 0.1; publishing them comes with the release. The compose file names the images as they will be published. |

## Design defaults

- **Package**:
  - SQLite by default; a `postgres` profile adds a PostgreSQL container with a password generated
    by the install script;
  - volumes for the data, the key and the runner;
  - the runner gets the Docker socket, as documented for the reference runner;
  - ports 5080 (UI and API) and 5081 (runners) by default, changeable in `.env`.
- **Install script**:
  - `install.sh` (POSIX sh) and `install.ps1` do the same;
  - no questions on the command line beyond the target directory and `--postgres`; everything else
    is asked in the browser;
  - running it again on an existing directory updates and restarts, and never overwrites `.env`.
- **Security**:
  - the setup token is compared in constant time and setup attempts are rate-limited;
  - finishing setup is one transaction;
  - the setup API is gone afterwards (`404`).
- **Tests**:
  - the server's setup mode on SQLite and PostgreSQL;
  - the wizard with Vitest and in Playwright;
  - the whole package in a CI job of its own: install, setup through the API, a run on the bundled
    runner.

## Steps

Each step is one PR into `main` unless noted.

### Step 1 — Plan and decisions

This plan and [ADR-0020](../adr/0020-first-start-setup.md).

### Step 2 — Setup mode on the server

- **Setup mode**:
  - the setup token and its log line;
  - `GET /api/v1/setup` (whether setup is open);
  - `POST /api/v1/setup` (admin, settings, runner token, example; with the token);
  - every other API request answered with `503` while setup is open.
- **Generated master key**, recorded like a configured one.
- **Instance settings**: table, migrations for both providers, `GET`/`PATCH
  /api/v1/admin/instance`, configuration winning over the database.
- **Handing the runner token over** to a file on a shared volume (`Setup:RunnerTokenFile`).
- **Tests** on both databases, the OpenAPI snapshot, operations and user docs.

### Step 3 — The wizard in the web UI

- **`/setup`**, outside the app shell:
  1. the token (filled in from the address);
  2. the first admin;
  3. the addresses, filled in from the browser;
  4. the bundled runner, waiting until it is online, or the commands for another runner;
  5. the example automation;
  6. a summary with the master key, shown once.
- After setup the browser signs in as the new admin.
- **Administration → Instance**: the addresses, locked where configuration sets them.
- Vitest, a Playwright spec with screenshots.

**Review**.

### Step 4 — Runner and compose package

- **Runner**: `Runner:RegistrationTokenFile` (wait for the file, register, run) and `Runner:Name`.
- **Package**: `deploy/compose/compose.yaml` with the server, the runner, volumes and the `postgres`
  profile.
- **Install scripts**: `deploy/install.sh` and `deploy/install.ps1`.
- **Forwarded headers** behind a proxy (`Server:TrustedProxies`): sign-in rate limits per client
  and full webhook addresses (carried over since S1).
- **CI job "Compose"**: the install script, setup through the API, a run of the example automation
  on the bundled runner, with and without PostgreSQL.

**Review**: Felix installs it on his machine.

### Step 5 — Close S4

- **Getting started**: a page on installing, the wizard and the first run, with pictures from a
  Playwright walk-through of the wizard against the compose package in CI.
- **Operations**: backing up the data and the key, updating, PostgreSQL, a proxy in front.
- Outcome and carry-over in this plan.

## Open questions

- **Bundled runner labels**: `linux` and `docker`, or chosen in the wizard? The runner announces
  its labels from its configuration, so choosing them would mean writing them to `.env` — proposed:
  fixed, changeable in `.env`.
- **Example automation**: proposed is one job on `alpine` that prints a greeting and writes a small
  JUnit and Cobertura report, so the first run shows the log, tests and coverage.

## Out of scope

- Published images, releases and a changelog (0.1).
- TLS inside the package; the docs show a proxy (Caddy, nginx) in front.
- Kubernetes and Helm.
- E-mail.
- OIDC.
- Several server instances in the package.

## S4 done when

- On a machine with Docker, the install script and the wizard lead in a few minutes to an instance
  with an admin, its address and a registered runner, on which the example automation runs.
- This runs in CI, with SQLite and with PostgreSQL.
- The getting-started docs show it with pictures.
