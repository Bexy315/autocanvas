# S5 — Repositories and forges

> Status: **in progress** · Created: 2026-11-04 · Owner: Felix

S5 brings automations that live in repositories ([ADR-0003](../adr/0003-pipeline-sources.md)):
- a repository is connected in a folder, and its `.autocanvas/automations/*.yml` show up there;
- pushes and pull requests start runs;
- runs report back to the forge;
- a repository automation edited in AutoCanvas becomes a pull request.

The automation format has had `triggers.push` and `checkout: self` since S0; the server learns what
they mean now.

As in S3 and S4, every step that changes what is visible ends with a **Review** point for the
maintainer.

## Fixed decisions

Felix decided these on 2026-11-04; [ADR-0021](../adr/0021-repositories-per-folder.md) and
[ADR-0022](../adr/0022-github-app.md) record the architecture.

| Topic | Decision |
|---|---|
| Forges | **Generic Git** (any repository over HTTPS, with a token or user name and password, webhook or polling) and **GitHub**. GitLab and Gitea follow later on the same abstraction; until then they work as Generic Git. |
| Connecting | **Per folder**: editors of a folder connect a repository there. Its automations appear in the folder read-only and inherit the folder's roles, variables and secrets. |
| GitHub | **One GitHub App per instance**, created from the UI with GitHub's manifest flow; installation tokens for the API, discovery and checkouts; one webhook for all events. |
| Pull requests | A `pull_request` trigger; the run's result as a **commit status**; one **comment** per pull request with tests and coverage, updated by later runs; **Edit → pull request** for repository automations. |

## Design defaults

- **Discovery** reads `.autocanvas/automations/*.yml` (and `.yaml`) at the default branch:
  - on a push to it, on demand (**Sync**), and on a poll for repositories without webhooks;
  - a file is one automation, named after the file without its extension;
  - its versions are the commits that changed it.
- **Runs of a repository automation** use the file at the commit they run for. A push to another
  branch or a pull request reads the file at that commit, for that run only.
- **Checkout**: `checkout: self` (the default for repository automations) gets the run's commit,
  with the repository's credential, only for that job.
- **Credentials** (Generic Git token or password, the GitHub App's private key and secrets) are
  secrets under the master key, never returned by the API.
- **Webhooks**: Generic Git gets a signed address per repository (like automation webhooks), with
  a GitHub-compatible push payload so a Gitea, GitLab or self-hosted hook can call it. The GitHub
  App has one address for the instance.
- **Tests**:
  - a local Git server in the tests (a bare repository served over HTTP by the test host);
  - a GitHub stub for the app's API and events;
  - in CI, the closing walk-through against a Gitea container as a real Generic Git server.

## Steps

Each step is one PR into `main` unless noted.

### Step 2 — Repositories with Generic Git

- **`AutoCanvas.Forge`**: the abstraction with capabilities, and Generic Git through the `git`
  command line (shallow fetches into a cache in the data directory); `git` in the server image.
- **Data**: repositories (folder, address, kind, credential, default branch, polling, webhook
  secret) and repository automations with their versions; migrations for both providers.
- **API**: connect a repository in a folder (Editor), sync, change, disconnect; list a folder's
  repositories; repository automations in the folder's automations, marked as such.
- **Discovery** at the default branch, with problems in a file shown like a managed automation's
  (diagnostics); runs by hand on a repository automation at the default branch's commit, with
  `checkout: self`.
- Tests on both databases against a local Git server.

- **2a done** (Forge, repositories, discovery):
  - **`AutoCanvas.Forge`**: `IForge` with capabilities; `GenericGitForge` with `ls-remote`, a shallow
    fetch into a bare copy, `ls-tree` and `cat-file`; git without prompts, only http(s), the
    credential as a header in its environment.
  - **`GitHttpServer`** in the test support: `git http-backend` behind Kestrel, with Basic
    authentication if asked, so tests talk to a real smart-HTTP Git server.
  - **Data**: `repositories` (credential encrypted like a secret, rotated with the master key),
    `automations.repository_id` and `source_path`, `automation_versions.commit_sha`, `runs.commit_sha`
    and `ref`.
  - **API**: `GET`/`POST /api/v1/folders/{id}/repositories`, `GET`/`PATCH`/`DELETE` and
    `POST …/sync` on `/api/v1/repositories/{id}`; automations carry `repository` (name, path, commit).
  - **Discovery**: new valid files become automations, changed ones versions at the commit (subject
    and author), removed ones are deleted; invalid files and name clashes are `problems`; a failed
    read only sets `lastError`. A folder with repositories is not empty.
  - `git` in the server image.
- **6a done** (Edit → pull request, server):
  - `POST /api/v1/automations/{id}/pull-request` (Editor): the file is checked as when saving; a
    branch `autocanvas/<automation>-<time>` from the current version's commit, the file committed
    with the contents API, a pull request into the repository's branch with who proposed it.
    GitHub only; managed and Generic Git automations get 409. Audit
    `automation.pull_request_proposed`.
  - **Links** for the UI: `repository.kind`, `proposesChanges`, `webUrl`, `fileUrl`, `commitUrl` of
    a repository automation; `webUrl` of a repository; `commitUrl`, `pullRequest`,
    `pullRequestUrl` of a run; `pullRequest` in run lists.
- **5b done** (reporting back):
  - **Commit statuses** for every run of a GitHub repository automation with a commit: pending at the
    start, success, failure or error at the end, context `AutoCanvas / <automation> (<event>)`,
    a description with duration and failed tests, a link to the run with a public address.
  - **One comment per pull request** (`pull_request_comments`, marker `<!-- autocanvas -->`) with
    the latest run of each automation for the head commit, its tests and line coverage; updated by
    later runs, written anew when deleted.
  - **Outbox**: `runs.reported_state`; `ForgeReporter` runs in the repositories' background round,
    takes each change with a conditional update, reports once; failures are logged, not retried.
    Generic Git is passed over. `GitHubForge` now has the capabilities statuses, comments, pull
    requests.
  - Deviation: two runs of one pull request that end in the same round on two servers could each
    write a new comment; with one server, rounds are serial.
- **5a done** (pull request triggers):
  - **Format**: `triggers.pull_request` with `branches` (target branch), `paths` and `types` (opened,
    synchronize, reopened by default; also ready_for_review, edited) in Core, the schema and the
    canvas panel; `trigger.*` of a pull request.
  - **Events**: the GitHub App's `pull_request` events go through `repository_pull_requests` to the
    background handling; the files at `refs/pull/{n}/head` run when their trigger there matches,
    changed files from GitHub's list of the pull request's files. A moved head starts nothing;
    deliveries count once.
  - **Forks**: `runs.secrets_withheld`: `secrets.*` read as empty, no checkouts of other
    repositories. Every GitHub checkout uses a read-only token for the one repository.
  - `runs.repository_id` and `pull_request` for the reporting of 5b.
  - Deviation: no extra deduplication by head commit beyond delivery ids; a pull request edited
    without new commits starts runs only when its trigger asks for `edited`.
- **4b done** (Administration → Forges):
  - **Without an app**: create it (organization, GitHub Enterprise address) or enter an existing one
    (App ID, key as text or `.pem` file, webhook secret). **With the app**: its owner, id, events
    address, installations and the link to install it elsewhere; a new key or secret; remove.
  - **The way to GitHub**: the UI's policy allows forms to its own origin only, so it posts the
    manifest's state to `/api/v1/forges/github/manifest/launch`, a server page with a policy of its
    own (its one script by hash, forms to that GitHub only) that posts the manifest on. GitHub sends
    the browser back to `/admin/forges/github/created`, which finishes the app once.
  - e2e `13-forges` runs the whole flow against a GitHub stand-in in Node (`e2e/githubStub.ts`), with
    the pictures for `docs/user/github.md`.
- **4a done** (GitHub App, server):
  - **Forge**: `GitHubClient` (manifest conversion, app, installations, installation tokens,
    repositories; GitHub's message in every failure), `GitHubJwt` (RS256 by hand, no new
    dependency), `GitHubForge` (git over https with the installation token).
  - **App** (admin): created with the manifest flow (`/forges/github/manifest`, `/created`, the state
    encrypted with the master key, an hour) or entered by hand (`PUT`, checked with `GET /app`);
    `github_apps` with the key and secrets encrypted, rotated with the master key; removed only
    without GitHub repositories. GitHub Enterprise through `webAddress` and `apiAddress`, untested.
  - **Tokens**: `GitHubTokens` caches installation tokens until five minutes before they expire and
    remembers the one before for masking. `RepositoryCredentials` gives every repository its
    credential (stored or installation token) for discovery, polling, pushes and checkouts.
  - **Repositories**: `GET /folders/{id}/github/repositories` and
    `POST /folders/{id}/repositories/github` (Editor); `repositories.installation_id` and
    `external_id`; a GitHub repository takes no credential.
  - **Events**: `POST /forges/github/events`, signed, once per delivery (`github_deliveries`, three
    days), 600 a minute; pushes go through `repository_pushes` to every folder the repository is
    connected in; uninstalled or suspended installations set `lastError`.
  - Tests against `GitHubStub` (TestSupport): the app's JWTs and tokens checked as GitHub does, its
    repositories in a `GitHttpServer` that takes only the token.
- **3b done** (webhook per repository):
  - **Address**: `POST`/`DELETE /api/v1/repositories/{id}/webhook` (Editor), token `acg_` (hash
    stored) and a secret encrypted under the master key, both shown once; the repository shows its
    hint. Audit `repository.webhook_created|deleted`.
  - **Calls** on the existing `POST /api/v1/hooks/{token}`, told apart by the prefix: GitHub and
    Gitea/Forgejo (`X-Hub-Signature-256`, `X-Gitea-Signature`) and GitLab (`X-Gitlab-Token`); `ping`
    and other events answer 200 without doing anything. A push is stored in `repository_pushes`,
    answered at once and handled in the background (woken at once, every 5 s for other servers),
    through the same handling as polls: one run per push whichever sees it first. Changed files come
    from the payload's commits (unknown for new refs, forced pushes, 20 commits or more).
  - **Late deliveries**: a webhook for a commit older than one already handled starts nothing and
    leaves the ref at the newer commit, so the next poll does not run it again.
  - **Also fixed**: rotating the master key now re-encrypts webhook secrets, of repositories and of
    automations (signed automation webhooks failed after a rotation); the forges' signature and
    token headers are kept out of an automation webhook's `trigger.headers`.
- **3a done** (pushes and polling):
  - **Forge**: lists branches and tags (annotated tags as their commit), reads automation files at a
    tag or full ref, and the changed files between two commits (fetched 50 commits deep, unknown
    beyond).
  - **Pushes** (`RepositoryPushes`): each new commit of a ref starts its runs once, whoever sees it
    first moving the ref's row in `repository_refs`. A push to the repository's branch syncs first;
    every repository automation whose file exists at the pushed commit and whose `push` trigger
    there matches (branch and tag patterns, paths when the changes are known) runs that file at that
    commit, as the pusher (the author when polled). Deleted refs and the refs at connect start
    nothing. `trigger.*` of a push and `run.branch`, `run.commit_sha`, `run.commit_short_sha`
    resolve.
  - **Polling** every `pollMinutes` (default 5, 0 = off) by a hosted service every 30 s, each due
    repository taken with a conditional update; a failed poll sets `lastError`, the next good one
    syncs. A repository without recorded refs (connected before this step) records them on its first
    poll without runs.
  - **Core**: `Glob` (`*`, `**`, `?`) and `PushTrigger.Matches`.
- **2b done** (runs and read-only):
  - **Read-only**: saving, renaming, moving and deleting a repository automation is refused (409)
    with where it comes from; checking its file still works.
  - **Runs** of a repository automation keep the commit of its current version and the branch
    (`runs.commit_sha`, `ref`; the run's view shows them). `RunStart` takes a commit and ref for the
    push triggers of step 3.
  - **Checkouts** (`JobOfferBuilder`): by default and for `self` the run's commit with the
    repository's credential; a repository's name from the run's folder or above with its credential;
    https addresses without. The credential travels in the protocol's existing `username` and
    `password` and the server masks every credential the run's folder can use in the log.
  - Deviation: no Docker test of the runner checking out from the test Git server, since a container
    cannot reach the test host's loopback address the same way on every platform; the runner's
    checkout with a credential is tested since S2, and the closing walk-through (step 7) checks out
    from a Gitea container.

### Step 3 — Push triggers

Split into **3a** (handling pushes, polling) and **3b** (the webhook per repository).

- **A signed webhook per repository**, with a GitHub-compatible push payload. A push to the default
  branch runs discovery first.
- **Polling** for repositories without a webhook (default every 5 minutes, per repository).
- **Filters**: `triggers.push` with branches, tags and paths.
- **`trigger.*`**: the commit, ref, author and message.
- Deduplication when a webhook and a poll see the same push.

### Step 4 — GitHub App

Split into **4a** (the server) and **4b** (**Administration → Forges** in the web UI, with the
manifest flow in the browser), with the Review after 4b.

- **Administration → Forges**: create the app with the manifest flow, or enter an existing one; show
  its installations.
- **In a folder**: connect a repository from an installation.
- **Events**: push and pull request through the app's webhook, deduplicated by delivery.
- **Installation tokens** for the API, discovery and checkouts.
- Tests against a GitHub stub.

### Step 5 — Pull requests and reporting back

Split into **5a** (pull request triggers) and **5b** (statuses and the comment).

- **`triggers.pull_request`** (branches, paths, events such as opened, synchronized, reopened) in the
  schema, Core and the server; `trigger.*` with the pull request's number, branches and title.
- **Commit status** for every run of a repository automation, linking to the run.
- **A comment per pull request** with each automation's result, tests and coverage, updated by later
  runs.
- Pull requests from forks run without secrets, unless a later decision says otherwise.

### Step 6 — The web UI for repositories

- **In a folder**: connect a repository (Generic Git or from the GitHub App), see its state (last
  sync, problems, webhook address shown once), sync and disconnect.
- **Repository automations**: read-only with their commit and branch, runs and reports as usual, a
  link to the file on the forge.
- **Edit → pull request**: the editor opens a repository automation for editing; saving creates a
  branch with a commit and opens a pull request through the forge, then links to it. Forges without
  pull requests say so.

**Review**.

### Step 7 — Close S5

- **Walk-through in CI**:
  - against a Gitea container as Generic Git: connect, discover, push, run with checkout;
  - against the GitHub stub: app, pull request, status, comment, edit → pull request.
- **Docs**: a user guide page on repositories with pictures, and the operations of forges
  (addresses, polling, secrets).
- Outcome and carry-over in this plan.

## Open questions

- **Polling interval**: proposed default 5 minutes, per repository.
- **Secrets for pull requests from forks**: proposed no, as in GitHub Actions.

## Out of scope

- GitLab, Gitea and Bitbucket as full forges (they work as Generic Git).
- Check annotations per failed test.
- Automations outside `.autocanvas/automations/` (monorepo paths).
- Testing GitHub Enterprise Server.
- Several GitHub Apps per instance.

## S5 done when

- A repository connected in a folder shows its automations; a push runs them with the pushed commit
  checked out.
- With the GitHub App, a pull request runs them, gets a commit status and a comment with tests and
  coverage, and an automation edited in AutoCanvas becomes a pull request.
- Both run in CI, against a real Git server and the GitHub stub.
- The docs show it.
