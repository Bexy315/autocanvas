# S0 — Foundation

> Status: in progress (Step 4) · Created: 2026-10-29 · Owner: Felix

S0 turns an empty repository into a project with a clean skeleton, enforced quality gates, agent
guidance, a documentation site, the two core specifications (pipeline schema, runner protocol), and
the first harvested domain code — all green in CI. No server, UI or runner functionality yet.

## Background

AutoCanvas starts as a **clone** of the automation engine, runner and integration-test report
parser of a private homelab platform. After the initial migration, development is **fully
independent**: no shared code, no compatibility layer, no plugin seam for the homelab. Features may
be copied across by hand in either direction.

The goals that differ from the origin and shape every decision here:

- **Standalone**: simple setup, own auth, no external platform services.
- **Code quality**: strict gates from the first commit; documentation is part of done.
- **Performance**: measurable, and the runner protocol must allow non-.NET runners (e.g. Rust).
- **Open source** (MIT): audience is developers and technicians who need to automate things.

Working name is `AutoCanvas` (namespaces `AutoCanvas.*`, npm `@autocanvas/*`). It may change before
the first public release; ADR-0002 records that.

## Fixed decisions

| Topic | Decision |
|---|---|
| Relationship to origin | Clone once, then independent (ADR-0001) |
| License | MIT |
| Repo | `Bexy315/autocanvas`, private until a first running state |
| Pipelines | Both: in-repo YAML (`.autocanvas/*.yml`) and managed (DB, edited on the canvas). One source per pipeline. |
| Forges | Generic Git + signed webhooks first; GitHub / GitLab / Gitea behind a capability-based abstraction later |
| Runner protocol | Versioned spec first (gRPC, `proto/runner/v1`); the .NET runner is a reference implementation |
| Job dispatch | Own Postgres queue (`FOR UPDATE SKIP LOCKED`), no Hangfire for dispatch |
| Database | PostgreSQL only (v1) |
| Docs | Docusaurus in `docs-site/`, deployed to GitHub Pages by GitHub Actions (public, also while the repo is private) |
| Dev process | Felix + coding agents; `AGENTS.md` canonical, `CLAUDE.md` imports it; skills in `.claude/skills/` |
| Coverage gate | ≥ 75 % line coverage per component (.NET and web), enforced in CI |

## Out of scope for S0

Server/API, persistence schema, auth and permissions (S1); runner and queue (S2); web UI and canvas
(S3); setup wizard and packaging (S4); forge integrations (S5). Semgrep/Trivy scans, AI agent steps
and every homelab integration are not migrated at all.

## Steps

Each step is one PR into `main` (branch protection on, required checks green). Step order matters:
gates exist before code, specs exist before harvested code is adapted to them.

### Step 1 — Repository bootstrap

- Private repo `Bexy315/autocanvas`, `main` default branch.
- `LICENSE` (MIT), `README.md` (what it is, status: pre-alpha), `.gitignore`, `.editorconfig`,
  `.gitattributes` (LF everywhere).
- This plan in `docs/plans/s0.md`.
- Branch protection on `main`: PR required, required status checks, linear history.

### Step 2 — Skeleton with quality gates

.NET (`net10.0`, pinned via `global.json`):

- `Directory.Build.props`: `Nullable=enable`, `TreatWarningsAsErrors=true`,
  `AnalysisLevel=latest-all`, `EnforceCodeStyleInBuild=true`,
  `GenerateDocumentationFile=true` (CS1591 is an error for `src/` libraries — public API needs
  XML docs), deterministic + `ContinuousIntegrationBuild` in CI.
- One additional analyzer package (Meziantou.Analyzer) with a reviewed `.editorconfig` severity set;
  every suppression needs a justification comment.
- Central package management (`Directory.Packages.props`), lock files (`RestorePackagesWithLockFile`).
- Test stack: xUnit v3 on Microsoft.Testing.Platform (VSTest is no longer supported for xUnit v3
  on the .NET 10 SDK), Shouldly, coverlet.MTP for coverage and the threshold, ReportGenerator for
  the merged report.
- `nuget.config` with nuget.org only, so machine-wide feeds cannot leak into builds.
- Empty `AutoCanvas.Core` + `AutoCanvas.Reports` with one real test each so the gates bite.

CI (`.github/workflows/ci.yml`, runs on PR and `main`):

1. `dotnet format --verify-no-changes`
2. `dotnet build -c Release` (warnings are errors)
3. `dotnet test` with coverage → fail below 75 % line coverage per project (MTP exit code 14);
   coverage summary in the job summary
4. gitleaks (secret scan)
5. License check of dependencies (only MIT-compatible licenses allowed; list in `docs/technical/dependencies.md`)
6. Conventional Commit check on the PR title (squash merges)

Plus: `codeql.yml` (C#, later JS/TS; skipped while the repo is private because code scanning on
private repos needs GitHub Advanced Security), Dependabot (grouped, weekly — built in, no app to
install), PR template with the Definition of Done checklist.

The web gates (TS strict, oxlint + Prettier, Vitest ≥ 75 %, Playwright smoke) are specified here but
switched on when `src/web` appears in S3. Rust gates (`clippy -D warnings`, `rustfmt`, coverage via
`cargo-llvm-cov`) are switched on with the first Rust code.

### Step 3 — Agent guidance

- **`AGENTS.md`** (root, short and normative):
  - project purpose in three lines, layout map, how to build/test/lint locally (exact commands)
  - coding rules: no I/O in Core, public API documented, tests next to behavior, no new dependency
    without license check + ADR if architectural
  - Definition of Done: gates green · tests for new behavior · user/technical/code docs updated ·
    ADR for architectural decisions · plan file updated
  - workflow: branch per change, Conventional Commits, PR via `gh`, Felix merges
- **`CLAUDE.md`**: `@AGENTS.md` plus Claude-only hints (skills, hooks).
- Nested `AGENTS.md` per area as each area appears (`src/AutoCanvas.Core/AGENTS.md` in S0).
- **Skills** (`.claude/skills/<name>/SKILL.md`), first set:
  - `quality-gates` — run exactly what CI runs, locally, and interpret failures
  - `write-adr` — ADR template, numbering, status lifecycle
  - `docs-update` — which doc type a change touches and where it lives; regenerate references
  - `harvest` — rules for moving code from the origin: copy file, strip origin-specific parts,
    adapt to specs, add tests to the gate, never copy config/secrets/hostnames
  - later: `add-node-type`, `add-migration`, `proto-change`
- Optional hook: format-on-edit for `.cs`/`.ts` to keep agent diffs clean. *Deferred:* `dotnet format`
  loads the whole solution (several seconds per edit); revisit when the web UI arrives, where
  Prettier per file is cheap.
- Skills live in `.claude/skills/`; `AGENTS.md` lists them so agents other than Claude Code read the
  same playbooks.

### Step 4 — Documentation site and ADRs

- `docs/` holds plain Markdown (agents read it directly); `docs-site/` is a Docusaurus app that
  renders `docs/user`, `docs/technical`, `docs/adr`, `docs/protocol` as separate sections.
- `docs.yml`: on PR → typecheck + build with broken links/anchors/images as errors; on `main` →
  deploy to GitHub Pages (`https://bexy315.github.io/autocanvas/`, public while the repo is private).
- Docs are CommonMark (`markdown.format: detect`), so files render the same on GitHub and the site.
  `docs/plans/` is excluded from the site; published docs must not link to it.
- TypeScript is pinned to 5.9 in `docs-site/`: `@docusaurus/tsconfig` still sets `baseUrl`, which
  TypeScript 7 removed.
- Generated reference (pipeline YAML reference from `schema/pipeline.v1.json`, later node reference
  from node manifests, protocol reference from `.proto`) is produced by a script; CI fails if the
  committed output is stale.
- Code docs: the DocFX/API reference is generated from XML docs later (S1) — in S0 the
  CS1591 gate guarantees the comments exist.
- ADRs written in S0:
  - ADR-0001 Clone and diverge from the origin
  - ADR-0002 Working name AutoCanvas
  - ADR-0003 Pipelines: in-repo and managed, one source per pipeline
  - ADR-0004 Runner protocol: gRPC, spec-first, versioned
  - ADR-0005 Own Postgres job queue instead of Hangfire
  - ADR-0006 Quality gates and coverage threshold
- Technical doc stub: `docs/technical/architecture.md` (arc42-light: context, building blocks,
  runtime view of a run, deployment) — filled as milestones land.

### Step 5 — Specifications first

**Pipeline schema v1** (`schema/pipeline.v1.json` + `docs/user/pipelines.md`):

- Start from the origin's YAML model (`WorkflowModels.cs`, `WorkflowYamlParser.cs`, examples) and
  **review it deliberately** instead of copying: names, trigger model (manual, cron, webhook,
  push/PR later), jobs/steps/needs, services, outputs, `if:` expressions, variables/secrets
  references, `runs-on` labels, reports (`reports: [{format: junit, path: ...}]`).
- Version field (`version: 1`) and an explicit compatibility promise.
- The schema serves validation, editor autocomplete (VS Code `yaml.schemas`) and docs generation.

**Runner protocol v1** (`proto/runner/v1/*.proto` + `docs/protocol/runner-v1.md`):

- Registration (one-time token → runner identity/credential), heartbeat, capability/label
  announcement.
- Job lease via a long-lived bidirectional stream: offer → accept → lease renewal → completion;
  cancellation from the server; at-least-once delivery with idempotent completion.
- Log streaming in batched chunks with sequence numbers (resumable); step status events; outputs.
- Artifact and report upload (chunked, out of band of the control stream).
- Versioning and compatibility rules (additive changes only within v1).
- No implementation in S0 — `buf lint` + `buf breaking` run in CI from now on.

### Step 6 — Harvest 1: Core

From the origin (`services/automation/...`): `WorkflowYamlParser`, `AutomationValidator`,
`ExpressionEvaluator`, the DAG/ordering and output-mapping logic out of `WorkflowOrchestrator` and
`JobOutputMap`, `IntervalConverter`, `SecretRedactor`, YAML models.

- Adapt to the v1 schema; split orchestration **decisions** (pure: what runs next, given state) from
  orchestration **effects** (I/O, S1/S2). Only the pure part goes into Core.
- Remove every origin concept: object grants, folders-as-auth, notification/registry/agent nodes,
  homelab service clients.
- Tests: port existing tests where they exist, add table-driven tests for parser/validator/
  expressions; schema conformance test (every fixture validates against `pipeline.v1.json` and
  parses identically).
- Coverage ≥ 75 % (aim higher for Core — it is pure code).
- Small benchmark project (BenchmarkDotNet) for parse + validate of a large pipeline, recorded as the
  baseline in `docs/technical/performance.md`.

### Step 7 — Harvest 2: Reports

From the origin: `TestingReportParser` (TRX, Cobertura) and the result model used by the testing
collector. **Add JUnit XML** (the de-facto standard; the origin does not support it). SARIF is not
migrated.

- Normalized result model: suites, cases, outcome, duration, failure message/stack, attachments;
  coverage summary.
- Fixture-based tests with real-world reports (xUnit/NUnit/MSTest TRX, Maven/Gradle/pytest/Jest
  JUnit, Cobertura from coverlet/coverage.py), plus malformed and huge inputs (streaming parse,
  memory bound).
- User doc: supported formats and how to publish reports from a pipeline.
